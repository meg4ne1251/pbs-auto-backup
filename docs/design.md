# PBSの自動起動・停止

## 目的

専用の物理筐体で動くProxmox Backup Server（PBS）を、バックアップと必要なメンテナンスの時間だけ起動する。常時稼働するProxmox VE（PVE）から起動・監視・停止を制御し、消費電力を抑える。

この文書は要件と設計方針を整理したもの。初版のスクリプトと設定例は追加したが、サーバーへの設定変更とcronの登録はまだ行っていない。現行方針は2026-10-05の合意を反映している。導入手順は [setup.md](setup.md) を参照。

## 確定した条件

| 項目 | 内容 |
| --- | --- |
| 制御元 | PVE（現在1台） |
| 制御対象 | 単体で動く物理PBS |
| ストレージ | PBS内のZFS |
| 起動処理開始 | 毎日5:50 |
| バックアップ開始 | 毎日6:00（既存のPVE標準定期ジョブ） |
| 停止確認開始 | 毎日6:30 |
| 保守開始予定 | 毎月1日6:00 |
| 通常日の停止待ち上限 | 停止確認開始から6時間（通常は12:30まで） |
| 保守日の停止待ち上限 | 1回の監視は24時間（通常は翌日6:30まで）。継続中なら翌日のcronへ引き継ぐ |
| 起動方法 | Wake on LAN（WOL） |
| PBSへの接続 | SSH公開鍵認証 |
| WOL再送 | 送信から2分間ping応答がなければ再送 |
| アイドル確認 | 1分間隔で3回連続、停止条件を満たすことを確認 |
| 停止方法 | SSH経由で正常なシャットダウンを要求 |
| 停止要求の再確認 | 5分後もping応答があれば状態を再確認 |
| 翌朝の停止要求保留 | 標準設定では毎日5:40〜6:30。確認上限を変更した場合は開始時刻も連動 |
| 状態取得失敗 | 停止を保留し、連続アイドル回数をゼロに戻す |
| 記録 | ログのみ。通知は行わない |

時刻は運用時にPVEのタイムゾーンと照合する。6:30は停止確認を始める時刻であり、処理中なら停止せず待機する。6時間・24時間は処理終了を待つ上限であり、その時間まで必ず起動を維持する意味ではない。

## 実装範囲

- 本機能はPBSの起動・利用可能になるまでの確認・処理状態の監視・正常な停止を担当する。
- バックアップ開始はPVE標準の定期ジョブに任せる。本機能から開始・再実行は行わない。
- 当日のバックアップジョブやVM/CTごとの開始・終了・成功・失敗・未実施の判定は実装しない。その結果の記録もPVE/PBS側に任せる。
- バックアップ・reader・検証・GC・prune・同期などは、PBS全体の実行中タスクの有無で確認する。既知のタスク種別だけに限定しない。
- scrubなど、PBSタスク一覧に出ない保守処理は、それぞれの状態取得コマンドで確認する。実機で使っている処理と必要なコマンドは実装前に確定する。
- 手動停止抑止、offlineメンテナンスモードの設定・所有記録・回復は実装しない。既存のメンテナンスモードも変更しない。
- active operationsの追加確認、PVEジョブの完了照合、保守の未実施・再試行予定の追跡は初版に含めない。
- バックアップ結果、検証失敗、ZFSやSMARTの異常、容量不足などの診断・異常別の停止方針は本機能に追加しない。PBS側など既存の管理に任せる。
- 自動制御自身の起動結果・停止保留理由・状態取得エラー・監視終了理由・停止要求・到達不能の確認はログに残す。通知は行わない。

実行中タスクなしという判定は、当日のバックアップ全体の完了や、将来開始する処理がないことを保証しない。offlineモードや新規ジョブの開始抑止も使わないため、最終確認後に新しい処理が始まる可能性は残る。この範囲で簡潔な実装を採用する。

## 構成

- PVE側：起動用cron、停止確認用cron、WOL送信、PBSへのSSH接続、監視ループ、ログ。
- PBS側：SSHから呼び出す状態確認・停止用スクリプト。PBSタスクと、実機で対象としたZFS等の保守処理を確認する。
- SSH鍵には必要な操作だけを許可する。接続先のホスト鍵を確認し、無人実行でパスワード入力を待たない構成にする。

cronを入口とし、監視ループはスクリプト内で実行する。監視の二重実行を防ぐロックと、起動・停止要求の競合を防ぐ制御を設ける。長時間の監視によって翌朝の起動処理が実行できなくならないようにする。

## 起動フロー

1. 二重実行と停止要求との競合を確認する。
2. 既にPBSが利用可能なら、WOLを送らず準備確認へ進む。
3. PBSのMACアドレス宛てにWOLを送信する。
4. ping応答を待つ。2分間応答がなければWOLを再送する。
5. ping応答後、SSH接続、PBSサービス、対象ZFSプールとdatastoreのマウント状態を確認する。
6. 対象datastoreがバックアップに利用可能な状態になったことを確認し、起動完了を記録して起動プログラムを終了する。

ping応答だけで起動完了としない。WOL再送と準備確認には上限を設け、上限到達時は起動失敗をログに残して終了する。上限の具体値は未確定。起動が6:00に間に合わなくても、本機能からバックアップを再実行しない。

シャットダウン状態からのWOL対応と、送信元から対象NICへの到達性は実機で確認する。

## 停止フロー

1. 6:30に停止確認を開始する。前回から保守監視を引き継ぐ場合は、下記の引き継ぎ方針に従う。
2. PBS全体の実行中タスクを確認する。実行中タスクがあれば停止を保留する。
3. 対象のZFSプール等について、scrubなどの保留対象処理を個別コマンドで確認する。処理中や、一時停止された未完了scrubがあれば停止を保留する。
4. すべての対象で実行中処理がない状態を、1分間隔で3回連続確認する。処理を検出した場合や状態取得に失敗した場合は、連続回数をゼロに戻す。
5. 停止直前にも対象の状態を取得する。新しい処理や取得エラーがあれば監視に戻る。翌朝の停止要求保留時間帯は停止を保留する。
6. 停止条件を引き続き満たす場合、SSH経由で正常なシャットダウンを要求する。停止要求から到達不能確認が終わるまで起動処理との競合を防ぐロックを保持する。
7. 停止要求が受理され、pingの連続不応答を確認できた場合は保守引き継ぎ状態を解除して監視を終了する。SSH結果が不明な場合は到達不能になっても状態を維持する。明示的な拒否の場合は監視を続ける。
8. 停止要求から5分後も応答がある場合は、SSHで状況を再確認する。停止指示の再送が必要で、停止条件を引き続き満たす場合に通常の停止指示を再送する。再送上限は実装前に決める。

PBSタスクの確認には `proxmox-backup-manager task list --output-format json` を候補とする。実機のPBSバージョンに合わせ、全ユーザーの実行中タスクを取得できる権限・件数上限・取得結果の形式を確認する。状態取得に失敗したり結果を解析できなかったりした場合は、タスクなしと扱わない。対象プールが欠けた場合もアイドルと扱わない。

ZFS等の処理終了と、ストレージが正常であるかの診断は分ける。本機能は対象処理の実行状態を確認し、ストレージ異常の診断は行わない。

## 停止待ち上限と翌日への引き継ぎ

- 通常日は6:30から最大6時間待つ。処理終了を確認できないまま上限に達した場合は、理由をログに残して監視プログラムを終了する。PBSは稼働を維持し、次回の日次cronで改めて監視する。
- 保守は毎月1日6:00開始予定とする。保守処理を開始するジョブの配置と実行内容は別途決める。
- 保守日は6:30から最大24時間監視する。処理が終われば通常の停止判定を行い、24時間経過しても継続中・状態不明なら、PBSを停止せず翌日の停止確認cronへ監視を引き継ぐ。
- 保守監視の継続中は、翌日以降も1回24時間の監視を引き継ぐ。日付が2日になったことだけで通常日の6時間に切り替えない。
- 引き継ぎ用に保守監視の継続状態を記録する。監視が期限終了したことを保守完了と扱わず、正常な停止を確認するまで継続状態を維持する。引き継いだ監視は状態を新しく取得し、連続アイドル回数はゼロから数え直す。
- 翌日のcronは前回の監視の終了・ロック解放を待って開始する。同じ時刻に起動したからといって単にスキップし、監視担当がいなくなる構成にはしない。引き継ぎ待ちにも上限を設け、異常時はログに残す。
- 監視が翌朝まで続く場合、標準設定では毎日5:40〜6:30は停止要求を保留し、連続アイドル回数をリセットする。保留開始は5:50から停止確認上限と5分の余裕を引いた時刻とする。翌日の起動処理と6:00の標準バックアップ開始に停止処理が重ならないようにする。

24時間は1回の監視期間の上限であり、保守処理を強制終了したりPBSを強制電源断したりする期限ではない。

## 状態取得・停止失敗時の方針

- SSH接続失敗、コマンド失敗、権限不足、状態の解析失敗を「タスクなし」「処理終了」と扱わない。判断できない場合は停止を保留してログに残す。
- 起動待ち・停止待ち・停止要求後の到達不能確認には上限を設ける。上限に達しても強制電源断は行わない。
- 停止要求が明示的に拒否された場合は監視を続ける。SSH切断などで結果が不明な場合は後続の到達状態を確認するが、到達不能だけでは保守引き継ぎ状態を解除しない。
- ping断は到達不能の確認であり、物理的な電源OFFの確証とはしない。
- 本機能からofflineモードを設定しないため、その所有記録や解除・回復処理は設けない。

## 初版で確認するケース

- 別ユーザーのバックアップ、reader、検証、GC等が実行中なら停止しない。
- 対象のscrub等が実行中・一時停止中なら停止しない。
- SSH失敗、取得エラー、解析エラー、権限不足、対象欠落時に停止しない。
- 1分間隔で3回連続確認し、途中の処理検出や取得失敗で回数がゼロに戻る。
- 通常日の6時間上限で、PBSを停止せずログを残して監視が終了する。
- 保守日の24時間上限で、前回の監視が終了して翌日のcronへ引き継がれる。二重監視や、同時起動による引き継ぎ漏れがない。
- 保守継続状態と、翌朝5:40〜6:30の停止保留が引き継ぎ後も維持される。
- 停止要求時にSSHが切れても、その後の到達状態を確認する。停止できない場合も強制停止へ切り替えない。
- 既存PVEバックアップジョブの設定やPBSのメンテナンスモードを変更せず、通知を送らない。

## 実機導入前に確認・決定すること

- PVE/PBSのバージョン、PBSのIP・MACアドレス、WOL送信先ネットワーク。
- SSHユーザー、鍵、許可する操作。
- 起動準備確認の対象datastore・ZFSプールと、状態監視の対象プール。
- scrub等の保守処理の種類、毎月1日6:00に開始するジョブの配置と実行内容、状態取得コマンドと取得結果の形式。
- 全ユーザーのPBS実行中タスクを取得できる権限と、件数上限・ページング等の扱い。
- 起動待ちの上限、WOL再送回数、停止要求後の確認上限・再送回数、引き継ぎ待ち上限。
- ログの保存先・保持期間と、保守監視の継続状態の保存場所。
